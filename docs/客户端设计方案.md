# Arise 游戏客户端设计方案

> 版本: v1.1（已确认决策）
> 目标: 基于 Arise 分布式游戏服务器框架（C++ 服务端），设计并开发一个可联调、可演示的客户端。
> 对照物: 服务端自带 `bin/robots` 压测机器人（C++ 无头客户端），客户端须与其协议行为 1:1 对齐。

## 0. 已确认决策

| 项 | 决策 |
|---|---|
| 引擎 | **Unity 2021+（C#）** |
| 目标平台 | **Windows 桌面演示**（架构上保留 WebGL 中继扩展点） |
| 联调环境 | **allinone 与完整分布式都要支持**（服务器地址配置化） |
| 服务端小改（§6） | **同意一并实施**（创建角色后回发 PlayerList 等） |
| 代码仓库 | **独立仓库**（初始在 Arise 工作区内 `client/` 目录以独立 git 仓库形式落地，后续可整体迁出） |

## 1. 框架现状分析（客户端视角）

### 1.1 服务端拓扑

| 进程 | 作用 | 端口(默认) | 与客户端关系 |
|---|---|---|---|
| appmgr | 服务注册中心 / 世界实例分配 | 5500 | 间接（HTTP /login 入口，机器人用） |
| dbmgr | MySQL + Redis 持久化 | 5800 | 间接 |
| login | 账号验证 + 角色列表/创建/选择 + 下发 GameToken | 5401/5402 | **直接**（第一阶段） |
| game | 游戏逻辑（大厅代理、token 验证、玩家数据下发） | 5601/5602 | **直接**（第二阶段） |
| space | 世界场景模拟（进出图、AOI、移动权威） | 5701 | 间接（游戏服代理转发） |
| allinone | 全部合并单进程（测试模式） | 5401 + http 7071 | 直接 |

### 1.2 通信协议（必须精确实现）

**TCP + 自定义 4 字节帧头 + Protobuf 包体**（见 libserver/packet.h / network_buffer.cpp）：

```
帧结构（客户端与服务端之间，PacketHead 模式）:
┌────────────┬────────────┬────────────┬──────────────────┐
│ TotalSize  │ HeadSize   │ MsgId      │ Protobuf 包体     │
│ u16 LE     │ u16 LE = 2 │ u16 LE     │ 变长              │
└────────────┴────────────┴────────────┴──────────────────┘

TotalSize = 包体长度 + 2(MsgId) + 2(HeadSize) + 2(TotalSize) = 包体长度 + 6
HeadSize 恒为 2（sizeof(PacketHead)）；服务端进程间用 PacketHeadS2S(18B)，客户端永远用 PacketHead。
字节序：x86 小端，原样 memcpy，无网络序转换。
上限：TotalSize 为 u16，单帧 ≤ 65535 字节（protobuf 包体须 < 64KB）。
```

**编码/解码伪代码（C# / TS 通用）**：

```ts
// 编码
function encode(msgId: number, body: Uint8Array): Uint8Array {
  const total = body.length + 6;
  const buf = new Uint8Array(total);
  const dv = new DataView(buf.buffer);
  dv.setUint16(0, total, true);      // TotalSize
  dv.setUint16(2, 2, true);          // HeadSize
  dv.setUint16(4, msgId, true);      // MsgId
  buf.set(body, 6);
  return buf;
}

// 解码（粘包/半包处理）
// 循环: 缓存区 ≥2 字节读 TotalSize → 缓存区 ≥ TotalSize 时整帧取出
//   → 读 HeadSize(2B) → 读 MsgId(2B) → 剩余为包体
```

### 1.4 关键协议消息清单

| 方向 | MsgId | 消息 | 关键字段 |
|---|---|---|---|
| C→L | 1000 | C2L_AccountCheck | account, password(**MD5**，测试密码 123456 → e10adc...) |
| L→C | 1001 | C2L_AccountCheckRs | return_code（0=OK，2=无账号，3=密码错，4=登录中，5=超时，6=在线） |
| L→C | 1012 | L2C_PlayerList | account, player[]（sn/name/gender/level/last_world/last_dungeon） |
| C→L | 1014 | C2L_CreatePlayer | name, gender(1男/2女) |
| L→C | 1015 | C2L_CreatePlayerRs | return_code（0=OK，2=重名） |
| C→L | 1018 | C2L_SelectPlayer | player_sn |
| L→C | 1019 | C2L_SelectPlayerRs | return_code |
| L→C | 1024 | L2C_GameToken | return_code, **token, ip, port**（连接 game 用） |
| C→G | 1100 | C2G_LoginByToken | account, token |
| G→C | 1101 | C2G_LoginByTokenRs | return_code |
| G→C | 1106 | G2C_SyncPlayer | player（完整数据，sn/name/base/misc） |
| C→G | 1116 | C2G_EnterWorld | world_id, position（换图/进副本用） |
| S→C | 1501 | S2C_EnterWorld | world_id, position（进入世界通知） |
| S→C | 1503 | S2C_RoleAppear | role[]（name/sn/gender/position，可批量） |
| S→C | 1504 | S2C_RoleDisAppear | sn |
| C→S | 1505 | C2S_Move | position[]（**路点列表**，服务器权威推进） |
| S→C | 1506 | S2C_Move | player_sn, position[] |
| C→S | 101  | MI_Ping | 心跳（服务端收到即丢弃，仅保活） |

> 注：login 验证通过后先发 S2C_EnterWorld(roles 场景) 再发 L2C_PlayerList；客户端把"角色选择"当场景 2 处理。

### 1.5 世界与移动模型

- 世界配置：res/resource/world.csv — 1=login、2=roles、3=jiangxia(初始场景, 出生点 369.78,29.35,493.20)、4=dungeon02(副本)。
- 移动：客户端发**路点队列**（repeated Vector3），space 按 **速度 2 单位/秒** 沿路点逐段插值（X/Z 平面，Y 不变），每 500ms 推进一次；到达终点自动卸载移动组件。
- 出现/消失：space 有 _addPlayer 缓冲，定时批量广播 S2C_RoleAppear；离开广播 S2C_RoleDisAppear。
- Vector3 = float x/y/z（protobuf），注意服务端 Vector3 与 proto 字段对应。

### 1.6 服务端已知边界（客户端设计需适配）

1. **创建角色后不主动回发角色列表**：CreatePlayerRs 只含 return_code，无 sn；已确认服务端补发（§6）。
2. **验证超时/错误会直接断开 TCP**：客户端需实现"断线重连 + 重试登录"（超时后账号锁会清理，可重试）。
3. **单帧 < 64KB**：客户端序列化大包注意上限。
4. **心跳**：服务端对 Ping 只是忽略，不回应答；客户端按固定间隔发 Ping 保活即可（断线靠 TCP 检测）。

## 2. 客户端总体方案（引擎选型）

| 方案 | 语言 | 3D 能力 | 联调成本 | 生态/体积 | 适合度 |
|---|---|---|---|---|---|
| **Unity 2021+** | C# | ★★★ | 中（NuGet: Google.Protobuf） | 成熟，安装 ~2GB | ★★★★（已选定） |
| **Cocos Creator 3.x** | TS | ★★☆ | 中（protobufjs） | 轻量，国内流行，可发 H5/小游戏 | ★★★☆ |
| **Godot 4** | GDScript/C# | ★★☆ | 中 | 开源免费 | ★★★ |
| **Web(TS) + TCP中继** | TS | ★☆（Three.js） | 高（浏览器无裸 TCP，需 Node 中继转 WebSocket） | 轻 | ★★（多一层基础设施） |
| **Qt/C++ 桌面** | C++ | ★☆ | 低（与服务端同语言） | 重 | ★★（适合纯协议调试工具，不适合做游戏表现） |

**已确认：Unity 2021+（C#）**，理由：
- 3D 场景（jiangxia）表现与角色/移动同步是服务端现有能力的直接落点，Unity 是 3D MMO 事实标准；
- C# 与 protobuf（Google.Protobuf NuGet）集成成熟，可与服务端 build_c#.bat 生成同一套 msg.cs/db.cs，协议零手写；
- 可打包 Win/Mac/WebGL 演示，WebGL 时用 WebSocket 中继方案可复用同一套逻辑层（网络层抽象接口即可）。

> 其余方案（Cocos/Godot/Web/Qt）保留为备选；网络层与 UI 层设计可在多引擎间复用。

## 3. 客户端架构设计（分层）

```
┌─────────────────────────────────────────────────────────┐
│ 表现层  Scene/Entity/Animator/Camera/特效                │
│   ├─ SceneManager（login/roles/jiangxia 场景切换）       │
│   ├─ EntityView（角色模型、名字、位置插值渲染）          │
│   └─ MoveRender（点击寻路 → 路点采样 → C2S_Move）        │
├─────────────────────────────────────────────────────────┤
│ 业务层  GameLogic（客户端状态机，见 §4.3）               │
│   ├─ LoginManager / RoleManager / GameManager / WorldMgr │
│   └─ 场景实体缓存（sn → EntityView，RoleAppear/DisAppear）│
├─────────────────────────────────────────────────────────┤
│ 协议层  Protocol（protobuf 生成类 + 消息注册表）          │
│   ├─ MsgId 枚举 + 编解码映射表（msgId ↔ 类型 ↔ 处理器）  │
│   └─ 消息分发（收到帧 → 查表 → 回调业务层）              │
├─────────────────────────────────────────────────────────┤
│ 网络层  Network（连接管理/封帧解帧/粘包/心跳/重连）       │
│   ├─ ITcpClient 抽象（真实 TCP 实现 / WebSocket 中继实现）│
│   ├─ FrameCodec（§1.2 编解码）                          │
│   └─ Connection（异步收发、超时、断线回调）              │
├─────────────────────────────────────────────────────────┤
│ 工具层  Config（服务端地址、world.csv 镜像）/Log/Timer   │
└─────────────────────────────────────────────────────────┘
```

### 3.1 网络层要点
- 单连接模型：**一条连接只服务一个阶段**（先连 login，拿到 GameToken 后断开、再连 game），不混用；
- 收包线程/协程：异步读 + 帧队列，主线程消费（Unity 中避免跨线程调 API）；
- 粘包半包：环形/字节缓冲，按 TotalSize 切帧；
- 心跳：10s 间隔发 MI_Ping；30s 无任何收包判定超时；
- 重连：登录失败/超时按指数退避重试（服务端超时保护已清理账号锁，可安全重试）。

### 3.2 协议层要点
- 用服务端 protobuf/build_c#.bat（或手写 .proto 构建）生成 C# 类，与 msg.proto/db.proto 同源；
- 客户端只实现**面向客户端**的消息（§1.4 清单），服务端内部消息（MI_*/L2DB_* 等）不注册，收到未知帧记日志；
- 所有 S2C 消息处理器集中注册，表驱动分发，便于与 robots 对照审计。

### 3.3 业务层状态机（客户端）

```
Idle ──► Login_Connecting ──► Login_Connected ──► Login_Logined
                                        │
                             ┌──────────┴───────────┐
                             ▼                      ▼
                    Roles_SelectPlayer      (验证失败→重连/提示)
                             │
                  CreatePlayer / SelectPlayer
                             ▼
                    Wait_GameToken ──► Game_Connecting ──► Game_Connected
                                                                 │
                                              ┌──────────────────┘
                                              ▼
                                     Game_Logined ──► Space_EnterWorld ──► InWorld
                                                                              │
                                                            Move(点选) / 换图(C2G_EnterWorld) / 断线
```

## 4. 核心模块详细设计

### 4.1 登录模块（阶段一：连 login）
1. 输入账号/密码 → 密码 **MD5** 后组 C2L_AccountCheck；
2. 等待 C2L_AccountCheckRs：
   - ARC_OK(0)：切换到"角色选择"场景（服务端已主动发 S2C_EnterWorld(world_id=2) + L2C_PlayerList）；
   - 其他码：UI 提示对应错误（2 无账号 / 3 密码错 / 6 已在线等），并可重试。

### 4.2 角色模块（场景 2：roles）
- 收到 L2C_PlayerList 渲染角色列表（头像占位 + 名字/等级/性别）；
- 无角色 → 输入名字选性别 → C2L_CreatePlayer → C2L_CreatePlayerRs(0=成功/2=重名)；
  - 服务端已确认补发 L2C_PlayerList（§6），客户端收到后自动进入选择；
- 点选角色 → C2L_SelectPlayer → 等 C2L_SelectPlayerRs(OK) → 等 L2C_GameToken（含 game ip/port/token）。

### 4.3 进游戏模块（阶段二：连 game）
1. 断开 login 连接，连 game ip:port；
2. 发 C2G_LoginByToken{account, token} → C2G_LoginByTokenRs(0=OK)；
3. 收 G2C_SyncPlayer{player} → 创建本地玩家数据（sn/name/base/misc）；
4. 等待 S2C_EnterWorld{world_id, position}（游戏服按 LastWorld 自动传送，通常 world_id=3 江夏）→ 加载对应场景；
5. 收 S2C_RoleAppear{role[]} → 实例化其他玩家（位置插值渲染）；
6. 进入 InWorld：可发 C2S_Move 移动、收 S2C_Move 同步他人移动、收 S2C_RoleDisAppear 移除实体。

### 4.4 移动同步（场景表现核心）
- 点选地面 → 客户端寻路（简化：直线/网格寻路均可）→ 采样路点（每 0.5~1s 一段）→ 组 C2S_Move{position[]}；
- 本地立即按路点播放动画移动（速度对齐 2 u/s 或稍快做前瞻）；
- 收到 S2C_Move{player_sn, positions} → 覆盖他人目标路点，用**线性插值 + 朝向**平滑；
- 服务器权威：他人坐标以 S2C_Move 为准，不做预测回滚（本框架简单移动模型够用）。

### 4.5 场景与资源
- world.csv 镜像为客户端配置表（id/name/出生点）；
- jiangxia 用 Unity 内置 Terrain/Prototype 占位（后续可替换正式美术资源，AbPath 字段预留）；
- 角色模型：占位 Capsule/简易人形，接入 Animator 的 Idle/Run。

### 4.6 UI 层
- 登录界面（账号/密码/服务器地址/连接按钮/错误提示）；
- 角色选择界面（列表、创建弹窗、进入按钮）；
- 游戏 HUD（自身名字、坐标调试、在线人数调试、断线重连遮罩）；
- 调试面板：协议收发日志（msgId + 十六进制），用于与服务端/机器人对照。

## 6. 服务端配合的小改动（已确认实施）

1. **创建角色成功后回发新角色列表**（L2C_PlayerList）：在 Account::HandleCreatePlayerRs 成功后复用查列表逻辑，客户端即可无缝继续选择角色，无需重登。**（必做）**
2. **（可选）CreatePlayerRs 增加 player_sn**：客户端可直接选中新角色，改动最小。
3. **（可选）心跳应答**：MI_Ping 回一个空包，客户端可更早发现半开连接。
4. **（可选）协议版本号**：登录包带 client_version，服务端拒绝不匹配版本，避免联调期协议漂移。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 帧大小超限（u16） | 协议层对包体长度断言；后续大同步拆分消息 |
| 客户端与服务端协议漂移 | 用同一 .proto 生成代码；M1 起做协议回放对照 robots 日志 |
| 3D 表现工作量膨胀 | 占位资源先行，表现与逻辑解耦，正式美术后置 |
| WebGL 无裸 TCP | 网络层抽象接口，预留 Node TCP→WebSocket 中继实现 |
| 移动/位置不同步 | 以服务器权威为准，客户端插值 + 定期校准 |
